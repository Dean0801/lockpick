# Lockpick v0.3 设计文档 — 智能检测 & 配置文件感知

## 1. 目标

减少误报，让 lockpick 真正理解项目中哪些依赖是「隐式使用」的 — 通过配置文件引用的插件、package.json scripts 中的 CLI 工具、monorepo workspace 结构。同时提供 `.lockpickrc` 项目级配置文件，持久化 ignore 规则等设置。

## 2. 功能范围

| 功能 | 优先级 | 说明 |
|------|--------|------|
| 配置文件感知 | P0 | 扫描 ESLint/Babel/PostCSS/Tailwind/Vite/Next/Webpack 配置文件中引用的插件 |
| scripts 感知 | P0 | 检查 package.json scripts 中使用的 CLI 工具包 |
| monorepo 支持 | P0 | pnpm/npm/yarn workspace 多包项目分析 |
| .lockpickrc 配置 | P0 | 项目级配置文件，支持 JSON + YAML 双格式 |

## 3. 架构方案

**方案 A：统一插件式扫描器（已选定）**

- JS/TS 配置文件 → 复用现有 `extract_imports_from_source()` 提取 import/require
- JSON/YAML 配置文件 → serde 解析后按约定字段提取插件名
- 可扩展：新增配置文件类型只需加一个扫描函数

## 4. 新增文件结构

```
src/
├── scanner/
│   ├── config.rs          # 配置文件感知扫描器
│   └── scripts.rs         # package.json scripts 感知
├── config/
│   ├── mod.rs             # .lockpickrc 加载入口
│   └── types.rs           # LockpickConfig 结构定义
├── workspace/
│   └── mod.rs             # monorepo workspace 检测与多包分析
```

## 5. 数据流变化

```
之前：
  JS/TS 源码 → oxc import 提取 → used 集合

之后：
  JS/TS 源码 → oxc import 提取 ─────┐
  配置文件 → 插件/preset 提取 ──────┤→ used 集合（合并）
  package.json scripts → CLI 提取 ──┘
```

## 6. 模块详细设计

### 6.1 配置文件感知（scanner/config.rs）

配置文件分两类处理：

**JS/TS 配置文件** → 复用 `extract_imports_from_source()`：

| 工具 | 文件名模式 |
|------|-----------|
| ESLint | `eslint.config.{js,mjs,cjs,ts}` |
| Tailwind | `tailwind.config.{js,ts}` |
| Vite | `vite.config.{js,ts,mjs}` |
| Next.js | `next.config.{js,mjs,ts}` |
| Webpack | `webpack.config.{js,ts}` |
| Babel | `babel.config.{js,cjs,mjs}` |
| PostCSS | `postcss.config.{js,cjs,mjs}` |

**JSON/YAML 配置文件** → serde 解析 + 按字段提取：

| 工具 | 文件名模式 | 提取字段 | 前缀补全 |
|------|-----------|---------|---------|
| ESLint | `.eslintrc.{json,yml,yaml}` | `extends`, `plugins` | `eslint-plugin-` / `eslint-config-` |
| Babel | `.babelrc`, `.babelrc.json` | `presets`, `plugins` | `babel-plugin-` / `babel-preset-` |
| PostCSS | `.postcssrc`, `.postcssrc.json` | `plugins`（对象 key） | 无 |

公共接口：

```rust
/// Scan config files in project root, return package names referenced
pub fn extract_config_deps(project_root: &Path) -> HashSet<String>
```

### 6.2 scripts 感知（scanner/scripts.rs）

从 `package.json` 的 `scripts` 字段中提取 CLI 工具包名。

**提取逻辑：**
1. 读取 `package.json`，serde_json 解析 `scripts` 对象
2. 对每个 script value，空格分割取第一个 token 作为命令名
3. 查「CLI 命令 → 包名」映射表处理常见别名
4. 不在映射表中的命令名直接作为包名

**常见 CLI 别名映射表：**

| 命令 | 包名 |
|------|------|
| `tsc` | `typescript` |
| `tsx` | `tsx` |
| `node` | (skip) |
| `npx` | (skip) |
| `cross-env` | `cross-env` |

公共接口：

```rust
/// Extract package names used in package.json scripts
pub fn extract_script_deps(project_root: &Path) -> HashSet<String>
```

### 6.3 monorepo 支持（workspace/mod.rs）

**检测逻辑：**

| 协议 | 检测文件 | 提取字段 |
|------|---------|---------|
| pnpm | `pnpm-workspace.yaml` | `packages` (glob 列表) |
| npm/yarn | `package.json` | `workspaces` (字符串数组或 `{ packages: [...] }`) |

**分析策略：**

- lockfile 解析只做一次（根目录共享）
- 每个 workspace 包独立执行：读取 package.json 依赖 → 扫描源码 → 扫描配置文件/scripts → 对比 unused
- 报告按 workspace 包分组显示

公共接口：

```rust
/// Detect workspace packages, returns list of package paths
pub fn detect_workspaces(project_root: &Path) -> Result<Vec<PathBuf>, String>

/// Check if project is a monorepo
pub fn is_monorepo(project_root: &Path) -> bool
```

### 6.4 .lockpickrc 配置（config/）

支持 `.lockpickrc.json` 和 `.lockpickrc.yaml`，项目根目录自动检测。

**配置结构：**

```rust
#[derive(Debug, Deserialize, Default)]
pub struct LockpickConfig {
    pub ignore: Vec<String>,
    pub skip_dev: bool,
    pub lang: Option<String>,
    pub format: Option<String>,
    pub extra_configs: Vec<String>,
}
```

**加载优先级：** CLI 参数 > .lockpickrc > 默认值

**加载逻辑：**
1. 在项目根目录查找 `.lockpickrc.json` → `.lockpickrc.yaml`（先找到的生效）
2. 用 serde_json 或 serde_yaml 解析
3. 与 CLI 参数合并（CLI 参数覆盖配置文件）

**示例 .lockpickrc.json：**

```json
{
  "ignore": ["husky", "lint-staged"],
  "skip_dev": false,
  "lang": "zh",
  "extra_configs": ["jest.config.ts"]
}
```

## 7. main.rs 变化

```
加载 .lockpickrc → 合并 CLI 参数
                ↓
检测 monorepo? ──→ 是 → 遍历每个 workspace 包分别分析
                ↓ 否
单包分析流程：
  1. 解析 lockfile
  2. 扫描源码 import（ESM + CJS + dynamic）
  3. 扫描配置文件引用的插件
  4. 扫描 scripts 引用的 CLI 工具
  5. 合并 used 集合
  6. 对比 unused / duplicates / size / vulns
  7. 输出报告
```

## 8. 测试策略

- 每个模块独立单元测试（fixture 驱动）
- 配置文件感知：准备各种配置文件 fixture，验证提取的包名
- scripts 感知：准备 package.json fixture，验证 CLI 命令映射
- monorepo：准备 workspace fixture 目录结构，验证包发现和独立分析
- .lockpickrc：验证加载、合并、优先级逻辑
- 集成测试：端到端验证完整分析流程
